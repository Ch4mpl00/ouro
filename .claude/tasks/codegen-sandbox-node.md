# Детерминированный узел вычисления, генерируемый на ходу через Codex

**Status:** pending — подход ЗАФИКСИРОВАН (Codex, без своей песочницы)
**Priority:** P2 (направление развития, не горящее; усиливает workflow DSL)
**Area:** agent / workflow DSL / codex service / MCP
**Created:** 2026-06-15

## Context

Сейчас в DSL (`packages/agent/src/workflow/dsl.ts`) единственный способ
«вычислить» что-то — `llm_compose` (LLM прозой трансформирует данные). LLM
ненадёжен в ТОЧНЫХ вычислениях: арифметика, агрегации/фильтрация по большим
спискам, точные операции над строками, дата-арифметика, парсинг, дедуп, join'ы,
обработка большого файла. Это ровно то, что код делает идеально и дёшево.

Нужна возможность **писать и исполнять код** для задач. Долгосрочная мотивация
— гонять систему на сложных агентских бенчмарках (пользователь назвал «OOLUNG»
— уточнить точное название/источник перед интеграцией).

**Что значит «детерминированный узел» здесь.** Детерминизм НЕ про реплей
трейса и не про то, что Codex пишет код предсказуемо. Детерминизм — в **пути
данных**: само вычисление над файлом делает КОД (разобрать, отфильтровать,
посчитать — детерминированно), а сырые данные **не проходят через контекст
LLM вообще**. Codex, который на ходу пишет этот код, И ЕСТЬ такой узел —
детерминированный узел вычисления, сгенерированный на лету. Это снимает мой
прежний неверный тезис про «компромисс»: цель направления тут достигается, код
делает работу детерминированно, генерация кода на ходу этому не мешает.

Бонусом это единственный способ работать с БОЛЬШИМ файлом: он физически не
влезет в контекст LLM — значит обрабатывать его можно только кодом.

## Решение (ЗАФИКСИРОВАНО)

Используем **Codex** как генератор+исполнитель кода в ЕГО собственной
песочнице. Свой sandbox и свой codegen-агент НЕ строим — Codex уже умеет
писать код, исполнять и чинить по ошибкам в ReAct-цикле, и сервис уже крутится
(`packages/codex`, zero-dep, + клиент `judging/codex-client.ts`). На droplet'е
Codex шарит ChatGPT-квоту пользователя (см. [[project_codex_judge]]).

### Контроль внешнего мира — архитектурой, не настройкой агента

Ключевое решение по безопасности: гранулярный доступ во внешний мир делаем НЕ
тонкой настройкой песочницы Codex (там `network_access` — всё-или-ничего), а
так:

1. **Сеть в песочнице Codex выключена полностью** (`network_access=false`,
   `--sandbox read-only` или `workspace-write`). Сгенерированный код локален:
   считает, читает/пишет файлы — но в сеть не ходит.
2. **Единственный выход во внешний мир — наш MCP** (`packages/mcp`). Codex-агент
   достаёт/отправляет данные через наши MCP-тулы, а наш MCP сам решает, что
   можно, а что нет (мы владеем allow/deny). Код считает локально над тем, что
   MCP принёс.

Так шлюзы под нашим контролем без своей песочницы.

### Доступ к файлам (проверено по доке Codex)

Read-доступ у Codex широкий во ВСЕХ режимах — официально `read-only` это «read
everywhere, write nowhere». Значит **большой файл читается кодом без возни**,
даже в строгом режиме. Запись — `cwd` + `$TMPDIR` + `/tmp` + `writable_roots`.
Всё это прокидывается нашим раннером (`codex exec --sandbox <mode> -c <k>=<v>`,
плюс `cwd` — см. `packages/codex/src/runner.ts:124-139`):
`-c sandbox_workspace_write.writable_roots=[...]`, `-c ...network_access=...`.

**Настоящая загвоздка — не песочница, а видимость файла контейнеру.** Codex —
отдельный контейнер; «read everywhere» = ФС контейнера codex. Файл, который
пишет agent-контейнер (напр. `storage/`), Codex увидит только если volume
примонтирован И в codex-контейнер. Это интеграционная работа, не настройка
sandbox.

## Как это ложится в workflow

Поток (файл на входе → файл на выходе, данные не трогают LLM):

```
planner → delegate_code_task("разбери файл IN.txt КОДОМ: найди строки где X=Y,
          сделай то-то; НЕ читай файл сам — обработай кодом и запиши результат
          в OUT.txt") → llm_compose(читает OUT.txt и формулирует ответ)
```

- Новый synthetic-tool (`synthetic-tools.ts`), напр. `delegate_code_task`:
  тонкая обёртка над `codexClient.run(...)`. `sandbox=workspace-write` (нужна
  запись результирующего файла), `network_access=false`, `approvalPolicy:
  "never"`. Возвращает путь к выходному файлу (+ короткий статус), НЕ сами данные.
- **Критичный контракт в промпте Codex'у** (verbatim, см.
  [[feedback_verbatim_protocol_prompts]]): «обработай файл КОДОМ, НЕ читай его
  содержимое себе в контекст, запиши результат в отдельный файл». Это то, что
  держит путь данных детерминированным и делает возможной работу с большим
  файлом (он не влезает в контекст). Без этого Codex соблазнится прочитать файл
  глазами — и весь смысл узла теряется.
- `createCodexClient` поднять из-под `judging/` в общий слой (уже не только
  judge им пользуется).
- `llm_compose` на следующем шаге читает выходной файл (через `read_file`
  MCP-тул) и формулирует ответ. Сырые данные в контекст LLM попадают только
  УЖЕ обработанными/сжатыми кодом, не целиком.
- Планнер строит `delegate_code_task → llm_compose`. ReAct-цикл write→run→fix
  ведёт сам Codex — нам строить не надо. Правка `planner.md`: КОГДА слать в
  Codex (точное вычисление/код/большой файл) vs `llm_compose` (прозовая
  трансформация маленького входа).
- Per-node judge: узел — чёрный ящик (input→output), `llm_agent`-подобный.
  JUDGE yes, PATCH no (реплей небезопасен) — см. [[per-node-judge-and-improver]].

## Acceptance

- `delegate_code_task` поверх `codex` сервиса; `createCodexClient` в общем слое.
  Песочница без сети, `approvalPolicy: "never"`, разумный `timeoutMs`.
- Наш MCP примонтирован/подключён к Codex как единственный сетевой шлюз
  (open: как именно — см. ниже), сеть песочницы выключена.
- Планнер умеет строить `delegate_code_task → llm_compose` и знает, когда это
  уместно. Verbatim-правка `planner.md`.
- Контракт «обработай кодом, файл сам не читай, результат в файл» соблюдается:
  выходной файл создан кодом, сырой вход не попал в контекст Codex (проверить по
  событиям/трейсу на тестовой задаче).
- Узел трассируется; per-node judge видит чёрный ящик, PATCH off.
- `pnpm typecheck` + `pnpm test` зелёные. Проверено на ≥1 реальной задаче, где
  `llm_compose` ошибался бы в вычислении (или нужна обработка большого файла).

## Открытые вопросы

- **Как подключить наш MCP к Codex.** Codex берёт MCP-серверы из `mcp_servers`
  в config.toml, но наш раннер зовёт `codex exec --ignore-user-config` (чтобы
  хостовый конфиг не протекал). Значит MCP надо прокинуть через `-c
  mcp_servers.<name>....` (наш config-passthrough это умеет) либо точечно
  ослабить `--ignore-user-config`. Решить при реализации.
- **Volume codex-контейнера** для файловых задач (общий с agent/storage).
- **Бенчмарк «OOLUNG»**: уточнить имя/формат, как загонять через signals/skills.
  Связать с `eval-agent-e2e`, `eval-longform-queries` при тестировании.

## Отклонённое (с обоснованием)

- **Своя песочница** (`isolated-vm` / QuickJS-WASM / Pyodide) + свой codegen
  ReAct-агент. Детерминизм пути данных у нас и так есть (вычисляет код, не LLM —
  через контракт промпта), шлюзы контролируем архитектурой (сеть-deny + MCP),
  файловый доступ Codex покрывает. Свой рантайм дал бы только реплеибельность/
  кеш/дешевизну исполнения — недостаточный повод строить его сейчас. Вернуться,
  если квота/стоимость Codex начнут мешать.
